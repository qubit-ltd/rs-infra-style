# 机械门禁与人工审查边界

本文件替代历史对齐设计，只规定机械检查的证据与输出边界。
编码要求及规则 ID 以 [编码规范](rust-coding-standard.md) 为准，模板以对应文件为准。
不从旧工具、legacy profile 或旧测试反推新的硬性编码要求。

## 确定性诊断

遵循“宁可漏报，不要误报”：只有能够证明规则适用且确实违反规范时，
才生成阻断性风格诊断。不能证明的宏展开、cfg、名称归属、测试访问边界、
文档来源和类型属性交给人工审查。候选不计为风格失败，也不能标记为规则通过。

文件读取或解析失败、无效配置、必需工具执行失败是执行错误；
明确说明路径、命令、退出状态和未检查范围，不能伪装成空发现或代码违规。

## 覆盖与证据

- 枚举所选 Cargo workspace 成员、targets、自定义入口及独立 fuzz crate，说明范围。
- 区分生产、外部测试、内部测试、inline 测试、benchmark、fuzz、example 与其他 Rust 源码。
- vendor/generated 按项目配置记录排除理由；生成源码的修复优先指向生成器。
- 文件头、明确的 import 形状、测试命名和源码重定向等确定性子项可机械检查。
- 类型职责、Rustdoc 语义、核心类型示例代表性、测试访问边界、内联收益和复杂度由人工判断。
- README 元数据、结构可机械检查；双语功能、限制和示例语义一致性由人工判断。
- ATTR-003 的覆盖率 cfg 例外须同时具备源码 allow 注释和项目 allowlist 的带理由条目。
- 配置豁免只影响其明确规则，不传递到文件头、导入等其他规则。

报告包含规范来源/版本、范围、逐规则机械覆盖、人工范围、发现、例外和执行错误。
机械检查通过仅说明已执行的确定性检查未发现违规；不证明全部规则通过。
审查覆盖完整与风格通过分别报告，未审语义不得填 PASS。

## 验证与发布

检查器实现变更运行当前 crate 自身的相关回归和 CI；不加入 downstream all-features 测试。
检查规则的正反例、宏/cfg 边界、CRLF、文件头年份、测试发现与读取失败，
并核对报告规则索引与编码规范一致。源码风格任务的验证按 VERIFY-001；
完整开发验收按 [开发验证](development-validation.md)，不得混淆两类任务。

编译后随二进制发布的规范快照须标明 commit 和摘要；这不改变 AI 审查工具
按 [远程消费协议](consumption.md) 每次检查 main 的要求。
